## 1. Одной строкой

Спринты 1 «движки», 2 «CRUD» и 3 «консоль» закрыты. Движки рейтинга и сеток покрыты на 100%, инфраструктура описана в Docker, схема БД развёрнута миграциями. `kttf-back` проводит турнир **целиком, от создания до начисленного рейтинга**: вход, клубы, игроки, турниры, жеребьёвка, снимок рейтингов, ввод счёта, продвижение по сетке, достройка плей-офф, таблицы, завершение и обсчёт. Добавились итоговые места и публичные результаты турнира. `kttf-front` показывает **публичную часть: календарь турниров, страницу результатов целиком и рейтинг по стране**, и в нём работает **консоль судьи в онлайн-режиме**: столы, очередь, быстрый ввод счёта, таблицы, разрешение равенства и завершение турнира. Заработал **второй экран зала**: столы, очередь и таблицы по публичному токену, живое обновление потоком SSE. **Спринт 4 «офлайн» закрыт по коду:** снимок турнира и приём очереди на сервере, Dexie с очередью на диске и автосинхронизацией в консоли, индикатор связи. Осталось поле — испытания на живом турнире с выключенным Wi-Fi. Заработал **публичный профиль игрока**: кривая рейтинга своим SVG, история турниров и встреч, личный счёт против соперника. **Кабинет заводит и правит профиль игрока (ТЗ 2.2) — заглушек во фронтенде не осталось.** Из интерфейса организатор **заводит турнир целиком** — форма ТЗ 4.2 с редактором схемы и предпросчётом движком (ADR-024) — и записаться на турнир: условия допуска, лист ожидания, состав и панель организатора (ТЗ 4.3), причём **правило допуска на экране и на сервере — один и тот же код** (ADR-029). **Проведение турнира тоже вышло в интерфейс** (ТЗ 4.1): публикация, открытие и закрытие записи, жеребьёвка с показом расстановки, старт и отмена — до 02.09.2026 ни одного из этих действий во фронтенде не было вовсе, и заведённый в форме турнир оставался черновиком навсегда. **Расстановку организатор правит руками** — обмен двумя игроками (ТЗ 5.3, ADR-033). **Турнир проведён на живой базе от входа по коду до начисленного рейтинга, числа сошлись с расчётом по формуле.** **Продукт целиком поднимается одной командой `docker compose up -d`** — база, миграции, API, статика и прокси. **Следующее — полевые испытания офлайна и спринт 5 «рейтинг в проде».**

## 2. С чего начать новую сессию

Прочитать по порядку: `CLAUDE.md` → этот файл → `docs/06-decisions.md`. Дальше по задаче — `03-tech-spec.md` и нужный раздел `02-requirements.md`. Этого достаточно, чтобы продолжить работу без пересказа от человека.

**Миграций в очереди нет.** Последняя — `20260903000000_password_auth`, применена 03.09.2026: добавила `User.login` и `User.passwordHash`, удалила таблицу `AuthCode` (ADR-034).

**Проверить, что всё живо:**

```
cd kttf-infra  && docker compose up -d && docker compose ps  # весь стек healthy
cd kttf-shared && pnpm test          # 427 тестов, покрытие 100%
cd kttf-back   && pnpm check:shared  # связка с общим кодом
cd kttf-front  && pnpm check:shared  # тот же SHA, что в kttf-back
cd kttf-back   && pnpm lint && pnpm typecheck && pnpm test   # 340 тестов
cd kttf-front  && pnpm lint && pnpm typecheck && pnpm test   # 202 теста. Тест precache собирает приложение сам, отсюда лишние секунды (ADR-032)
```

Фронтенд целиком: `cd kttf-front && pnpm dev`, дальше `http://localhost:5173`. Запросы к `/api` уходят на `localhost:3000` через прокси дев-сервера — CORS в бэкенде не включён и не нужен.

**На чистой машине** (репозитории только что склонированы). Нужны Node 24+, pnpm 11 и запущенный Docker Desktop. Все четыре репозитория клонируются рядом, в одну папку: пути между ними относительные.

```
git clone https://github.com/goats-web-studio/kttf-shared.git
git clone https://github.com/goats-web-studio/kttf-infra.git
git clone https://github.com/goats-web-studio/kttf-back.git
git clone https://github.com/goats-web-studio/kttf-front.git

cd kttf-infra  && cp .env.example .env && docker compose up -d
cd kttf-back   && cp .env.example .env && pnpm install
cd kttf-front  && pnpm install
cd kttf-shared && pnpm install
```

**Схему накатывает сам стек** — контейнер `kttf-migrate` (ADR-030), отдельного `pnpm db:migrate` больше не нужно. Продукт целиком открывается на `https://localhost`: сертификат Caddy выпускает сам, локально он самоподписанный. Команда `pnpm db:migrate` остаётся для случая, когда база нужна без стека.

**Windows со Smart App Control: `pnpm db:migrate` не сработает.** Prisma запускает `schema-engine-windows.exe`, он неподписан, и Application Control его блокирует — наружу это выходит как `spawn UNKNOWN`. Исключений для отдельных файлов у Smart App Control нет, а выключается он необратимо. Проверить: `HKLM:\SYSTEM\CurrentControlSet\Control\CI\Policy`, значение `VerifiedAndReputablePolicyState` равно `1`. Обход — прогнать миграцию из Linux-контейнера в сети `kttf-net`: во временной папке нужны `prisma/schema.prisma`, `prisma/migrations` и минимальный `prisma.config.ts`, дальше `npm i prisma@7.10.0 && npx prisma migrate deploy` при `DATABASE_URL`, указывающем на `kttf-postgres:5432`. `_prisma_migrations` ведёт сама Prisma, контрольные суммы совпадают с файлами репозитория. Приложения это не затрагивает: клиент ходит в базу через `@prisma/adapter-pg`, нативного движка в рантайме нет.

`.env` под гитигнором и по гиту не приезжает — запрет №9. Оба примера рабочие и согласованы между собой: пароль Postgres в `kttf-infra/.env.example` совпадает с тем, что зашит в `DATABASE_URL` файла `kttf-back/.env.example`. Меняете один — меняйте второй, иначе бэкенд не подключится к базе.

**Данные по гиту не переезжают.** Клубы, игроки и турниры лежат в томе Postgres на той машине, где их завели. На новой база пустая: схему накатит `kttf-migrate`, наполнять её нужно заново. Скрипта с тестовыми данными пока нет.

**Как войти на пустой базе** (кодов по SMS больше нет — ADR-034):

1. Зарегистрироваться на `https://localhost/sign-up`: логин, пароль от восьми знаков, телефон `+7XXXXXXXXXX`. Игроков в пустой базе ещё нет, привязку пропустить
2. Завести клуб — интерфейса для этого **нет**, только маршрут: `POST /api/v1/clubs` с токеном. Создатель становится владельцем клуба и с этого момента видит создание турниров и панель проведения
3. Игроков заводит владелец клуба из состава турнира или страницы игроков

Существующему аккаунту пароль задаётся командой `cd kttf-back && pnpm build && pnpm set-password <телефон|логин> <пароль> [логин]`. Регистрация такому человеку не поможет: его телефон уже занят им самим.

API целиком: `cd kttf-back && pnpm build && pnpm start`, дальше `curl http://localhost:3000/api/v1/health` — ожидается `{"status":"ok","database":"up"}`.

## 3. Где что лежит

Четыре независимых репозитория рядом, организация GitHub — `goats-web-studio` (ADR-001, ADR-012):

| Репозиторий   | Состояние                                                                           |
| ------------- | ----------------------------------------------------------------------------------- |
| `kttf-shared` | Движки, контракт API, конфигурация, документация, ADR-тесты. Работает               |
| `kttf-infra`  | Docker Compose, Caddy, Prometheus. Продукт целиком поднимается одной командой       |
| `kttf-back`   | Турнир целиком: домены, жеребьёвка, счёт, обсчёт рейтинга, результаты, экран зала   |
| `kttf-front`  | Публичная часть, кабинет с профилем игрока, консоль судьи, экран зала. Заглушек нет |

Верхний уровень (`kttf/`) — просто общая папка, не проект. Всё общее живёт в `kttf-shared`, включая эту документацию.

**Инфраструктура живёт в `kttf-infra` (ADR-012), поднята и работает:** `kttf-postgres`, `kttf-redis`, `kttf-minio`, `kttf-api`, `kttf-web` и `kttf-proxy` в сети `kttf-net` (`172.28.0.0/16`). Схема БД применена — 17 таблиц домена. Порты на хосте смещены: PostgreSQL `5433`, Redis `6380`; наружу смотрит только прокси на `80` и `443`.

### Что стоит знать про движок

- `calculateMatch` и `applyDelta` — весь публичный контракт
- Замкнутость обеспечена конструкцией: базовая величина считается один раз, округляется один раз, применяется с двумя знаками. Отдельной проверки «сошлось ли» нет и не нужно
- Расхождение дельт (`imbalance`) возникает **только когда провизорен победитель**. `K_PROV_LOSS` намеренно равен `K_BASE`, поэтому провизорный проигравший ведёт себя как обычный. Это неочевидно и специально закреплено тестом
- Тесты нашли реальный дефект: `-round2(0)` давал `-0`, который не равен `0` по `Object.is` и утёк бы в API и колонку `Decimal`. Закрыто функцией `negate`

### Что стоит знать про сетки

- Модуль ничего не знает об участнике, кроме `ParticipantId`: рейтинг и клуб приходят параметрами
- Места в таблице определяются не всегда. Неразделённые правилами 1–5 участники возвращаются в `unresolved`, решение судьи приходит на вход через `tieDecisions` — движок обязан оставаться детерминированным (ADR-008)
- `splitIntoGroups` не гарантирует разведения одноклубников: посев старше, оставшиеся совпадения возвращаются списком `clubCollisions` (ADR-011)
- `resolveBracketSlots` возвращает **только изменившиеся** слоты сетки и пересчитывает их из источников целиком — отсюда идемпотентность и правильная реакция на правку результата
- `selectAdvancing` отбирает вышедших из групп; равенство, задевающее зону выхода, останавливает отбор, равенство ниже неё — нет
- `validateMatchResult` — проверка счёта. Живёт здесь, потому что счёт вводят в офлайне

### Что стоит знать про турниры

- Реализовано из ТС 7.5 всё, кроме `snapshot` и `sync`: оба — офлайн-режим
- **Жеребьёвка полностью работает для круговой и олимпийки.** Для «групп + сетка» и «групп + финальные группы» она строит только групповой этап; плей-офф достраивается сам, когда групповой этап сыгран (ADR-020)
- **Утешительная сетка не строится** — движок её не умеет, а собирать сетку в приложении запрещено запретом №2. Жеребьёвка отвергает такую конфигурацию явным отказом
- Повторная жеребьёвка стирает предыдущую целиком (ТЗ 5.3). Случайный посев перемешивается до входа в чистую функцию, поэтому сама раскладка воспроизводима
- Состав группы отдельной колонкой не хранится: он выводится из её встреч
- `start` фиксирует `ratingAtStart` и `matchesAtStart` в одной транзакции с переходом — без этого корректность недостижима (ТС 5.4)
- Участник подтверждается сразу при записи, лист ожидания продвигается сам, удалить можно только черновик — ADR-018
- Дедлайн регистрации проверяется при записи, а не переводом статуса по расписанию: фоновых задач нет
- `formatConfig` разбирается Zod-схемой и при записи, и при чтении из базы

### Что стоит знать про ввод счёта

- **Состав сетки пересчитывается целиком из `sourceA`/`sourceB`, а не дописывается по одной встрече.** Один и тот же код обслуживает ввод, правку и отмену: изменившийся победитель едет вниз, ставшее неопределимым обнуляется (ADR-021)
- Плей-офф достраивается автоматически в той же транзакции, что и результат, закрывающий групповой этап. Неразрешённое равенство откладывает достройку, но **не ломает ввод счёта**: счёт пишется, причина возвращается в `blockedByTies` (ADR-020)
- Правка отклоняется, если на результате держится сыгранная встреча ниже. Несыгранный плей-офф при правке групповых результатов пересобирается молча
- Отмена возвращает встречу в очередь, а не выставляет `CANCELLED`: ТЗ 6.3 старше перечисления в схеме
- Счёт проверяется чистой функцией общего кода — та же проверка сработает в офлайн-консоли. Счёт внутри сета не проверяется: ТЗ его не задаёт
- Ввод счёта разрешён судье клуба-хозяина наравне с владельцем и организатором. Управление турниром судье по-прежнему закрыто
- `QUEUED` не используется: очередь консоли выводится из «оба игрока известны, результата нет». `PENDING` — ждёт, `PLAYING` — на столе, `FINISHED` — сыграна
- `AuditLog` начал заполняться — правками результата (ТЗ 6.3) и завершением турнира

### Что стоит знать про схемы проведения

- **Схема — это `formatConfig`, и второй модели быть не должно** (ADR-024). Его читают жеребьёвка, таблицы, места и будет читать офлайн-консоль
- **Длина встречи по кругам считается от финала назад.** Размер сетки при создании турнира неизвестен — он зависит от числа записавшихся. «Полуфинал» — это «предпоследний круг», а не «третий». Настройка «последние N кругов длиннее» работает при любом размере сетки
- **Между группами сравнивают по отношениям, а не по разностям.** Разности правил 4–5 ТЗ 6.6 честны внутри группы, где все сыграли поровну; между группами разного размера они дают фору тому, кто сыграл больше встреч (ТЗ 6.7, ОВ-16)
- Практика WTT: все встречи до пяти партий, полуфиналы и финал основной сетки — до семи. ITTF отбирает лучшие вторые места из групп по отношениям выигранных встреч, затем сетов, затем мячей
- Ручной посев номерами **уже работает**: `PATCH /tournaments/:id/registrations/:id`, дальше `seedParticipants` ставит расставленных вперёд в порядке организатора, остальных по рейтингу следом. Чего нет — правки уже готовой жеребьёвки
- **Дефект:** `consolation: true` схема принимает, жеребьёвка отвергает. Турнир создаётся и не разлагается
- В группах всегда один круг: `scheduleRoundRobin(participants, 1)` захардкожено

### Что стоит знать про итоговые места

- **Место считает стратегия на схему, а не общая функция** (ADR-023). Диспетчер — `Record` по союзу схем: добавить схему и забыть про её места не выйдет, не соберётся. Новая схема — новый файл рядом, существующие не трогаются
- Файлы лежат плоско в `src/brackets`, без подпапки: ADR-тест чистоты движков читает каталог без рекурсии, и подпапка вывела бы новый код из-под его надзора молча
- **Не вышедшие из группы места не получают**: `place: null`, причина `GROUP_EXIT`. Межгруппового сравнения нет ни в ТЗ 6.6, ни где-либо ещё
- Делёж мест (`shared`) и неразрешённое равенство (`unresolved`) — разные вещи. Первое разделить нечем по существу: полуфиналисты между собой не играли. Второе ждёт судью и держит завершение турнира (ADR-008)
- Диапазон мест круга вылета берётся из фактического числа проигравших, а не из размера круга: при свободных проходах их меньше, и формула оставила бы в таблице дыры
- **`Match.kind` движка в базу не пишется.** Встреча за третье место узнаётся по источникам: она единственная в сетке, куда едут проигравшие
- Схемы у конкурента — редактируемый пользователем список с импортом и экспортом, а не зашитый набор. Наши четыре схемы этому не мешают, но пресетами пока не являются

### Что стоит знать про завершение и обсчёт

- **Один маршрут `finish`, две транзакции** (ADR-022). Первая закрывает турнир, вторая начисляет рейтинг. Упавший расчёт оставляет турнир в «Завершён», повторный вызов доводит до «Обсчитан», ничего не пересчитывая. Переход в «Обсчитан» служит замком от гонки: он идёт первым и только из «Завершён»
- Завершение держат три вещи: несыгранная встреча, неразрешённое равенство (ADR-008) и сыгравший без снимка на старте. Последнее — не норма, а испорченные данные, и отказ громкий
- **Правило «этап сыгран» одно на двоих** — `stage-completion.ts`. По нему достраивается плей-офф и по нему же завершается турнир. В группах встречу снявшегося не ждут (ADR-009), в сетке ждут: без результата победитель не поедет дальше, техническую победу судья вводит явно
- Дельта считается против снимка, **применяется к текущей проекции** цепочкой. Провизорность тоже берётся из снимка: `K` не меняется по ходу турнира
- Порядок встреч структурный, не по времени: пересчёт истории обязан дать ту же цепочку событий
- Нулевая дельта от разрыва в 100 очков — событие в журнале и +1 к счётчику провизорности. Техническая победа и снятие — ни того, ни другого. Полная таблица отбора в ADR-022
- `imbalance` пишется только победителю: на обеих сторонах метрика вброса ТС 5.6 удвоилась бы
- **Проверено на живой базе 01.09.2026.** Два круговых турнира на четверых, целиком через API: вход по коду, клуб, игроки, запись, жеребьёвка, старт, счёт по шести встречам, `finish`. Сошлось всё, что моки не показывали:
  - дельты легли в `numeric(8,2)` без потери точности, `expected` и `gapMultiplier` — в `numeric(6,4)` и `numeric(5,4)`
  - `imbalance` заполнен ровно у победителей, `null` у проигравших: `createMany` кладёт `null` корректно
  - в каждом турнире сумма всех дельт в точности равна сумме `imbalance` — рейтинг входит в систему только через провизорный канал
  - цепочка `ratingBefore → ratingAfter` непрерывна в структурном порядке встреч, `Player.rating` совпадает с суммой журнала
  - повторный `finish` из «Обсчитан» отбит, журнал не удвоился — `updateMany` работает замком
- **Замкнутость проверена отдельным турниром.** На четвёрке новичков она недостижима в принципе: все провизорные, `K` расходятся 40/20. Двоим выставлено `ratedMatches = 25` прямо в базе, после чего их встреча дала `+5.25 / −5.25` и `imbalance` ровно `0.00`. Чтобы повторить, нужна та же ручная правка: круговая на четверых даёт по 3 встречи, до порога в 20 их семь турниров
- **Журнал не хранит порядок событий.** Все записи турнира вставляются одним `createMany` и получают одинаковый `createdAt`. Сортировка журнала по времени внутри турнира неоднозначна; порядок восстанавливается только через `matchId` — по этапу, кругу и позиции в сетке, то есть ровно так, как его строит движок. Для пересчёта истории (ТС 5.5, инвариант 8) это существенно

### Что стоит знать про общий контракт

- `@kttf/shared/types` — схемы и DTO трёх доменов: постраничность, ТС 7.1, ТС 7.2, ТС 7.4. Схемы описывают и запросы, и ответы; разбор ответа на клиенте необязателен, схема просто есть
- `Zod` — **peer-зависимость** общего кода. Приложение обязано поставить его само, иначе схема одной копии библиотеки не пройдёт `instanceof` в другой
- Серверное в общий код не переехало: TTL кода, токена и сессии остались в `kttf-back`, там же арифметика смещения для базы
- `role` и `gender` в ответах остались строками, а не перечнями, — так было до переноса. Ужесточение поменяло бы контракт, а это отдельное решение

### Что стоит знать про каркас фронтенда

- Маршруты разделены по четырём оболочкам: `_public`, `_app` (охрана в `beforeLoad`), `console`, `screen`. Оболочки несводимы намеренно — общая обёртка утянула бы зависимости публичной части в чанки консоли
- Компоненты маршрутов не экспортируются. Экспорт отключает вынос компонента в отдельный чанк — проверено, чанк исчезает и уезжает в основной бандл. Отсюда же выключенное правило `react-refresh/only-export-components` для `src/routes` (ADR-016)
- Service worker не обновляется сам: перезагрузка вкладки может застать судью посреди турнира
- Пользовательских строк в компонентах нет: тип ключа выведен из русского словаря, пропуск ключа в казахском не компилируется
- Refresh-токен лежит в `localStorage`, access-токен только в памяти; обновление прозрачное и одно на все параллельные запросы (ADR-017)
- Маршруты аутентификации помечены `anonymous`: без этого отказ на `/auth/refresh` запускает обновление, которое ждёт само себя

### Что стоит знать про публичные экраны

- Страница турнира берёт **один** маршрут — `GET /tournaments/:id/results`. Он отдаёт и турнир, и участников, и таблицы, и встречи, и рейтинги сразу. Разложить его на пять запросов означало бы пять моментов времени в одном ответе: счёт из одного, места из другого
- Ни одно число на клиенте не считается. Очки, разницы, места и `totalDelta` приходят посчитанными; рейтинги показываются строками как есть. Сложение строк через число с плавающей точкой — тот самый способ потерять сотую долю, ради которого рейтинг и передаётся строкой (ADR-014, запрет №2)
- Пустая секция — это ответ, а не пропуск: у олимпийки нет таблиц, у круговой нет сетки. Такие секции не рисуются вовсе
- Пустое место различает `GROUP_EXIT` и `UNDECIDED`, а делёжка мест показывается диапазоном. Одна пустая клетка на все случаи ничего человеку не объясняет
- Перечисления контракта переводятся через `Record<..., MessageKey>` в `features/tournaments/labels.ts`: новое состояние в общем коде ломает сборку здесь, а не выходит к человеку английской строкой из базы
- Названия клубов берутся справочником `GET /clubs` одним запросом на страницу: турнир несёт только `clubId`. Когда клубов станет больше сотни, название придётся отдавать вместе с турниром
- **Оборванная ссылка объясняется словами, а не общим текстом проверки схемы.** Неверный по форме идентификатор сервер отвергает как `VALIDATION_FAILED`, и его общий текст — «проверьте заполненные поля» — выходил на страницы, где полей нет вовсе; на экране зала это висело на телевизоре. Проверка кода общая (`common/api/isMissingResource`), текст у каждой страницы свой: не найтись может игрок, турнир или экран
- Фильтры страниц живут в состоянии компонента, а не в адресе. Ссылка на отфильтрованный календарь пока не пересылается — это осознанное упрощение, а не недосмотр
- Из таблицы рейтинга фамилия ведёт на профиль игрока (ТЗ 9.3). На странице результатов турнира ссылок на профиль по-прежнему нет: имена там приходят картой `names`, и ссылка потребовала бы протащить идентификатор через места, таблицы, сетку и журнал сразу — отдельная правка, а не побочная
- Казахские строки написаны агентом и носителем языка не сверялись

### Что стоит знать про консоль судьи

- **Ни одно действие не ждёт ответа сети** — запрет №1 действует уже в онлайн-режиме, а не с приходом офлайна. Счёт применяется к снимку сразу, запрос уходит следом. Это закреплено тестом, в котором сервер не отвечает вовсе, а счёт обязан оказаться на экране
- **Отказ ничего не откатывает.** Введённое судьёй остаётся и попадает в список неотправленного с повтором. Молчаливый откат означал бы, что счёт исчез сам, и судья узнал бы об этом в конце турнира. Список живёт в памяти до перезагрузки — это зачаток очереди синхронизации, а не она сама
- Ответ `MatchUpdateResult` применяется целиком: `updated` и `nextStage` подставляются в снимок, турнир не перезапрашивается. Ради этого сервер их и возвращает
- Состояние берётся из публичного `GET /tournaments/:id/results` — своего снимка у консоли пока нет. Лишнее в ответе — журнал рейтинга. Снимок появится вместе с офлайном (ТС 6)
- Опроса по таймеру нет намеренно: источник истины в зале — судья, и опрос перетирал бы только что введённое
- Зона столов различает **три** состояния, а не два: свободен, занят, встреча закрыта и ждёт освобождения. Сервер не снимает номер стола при вводе счёта, и это верно — в зале стол занят, пока за него не сели следующие
- Очередь сортируется по моменту, с которого свободны **оба** игрока; не игравший вовсе идёт первым. Отсюда и потребовались `startedAt` с `finishedAt` в контракте
- Быстрые кнопки выводятся из `setsToWin` схемы: при трёх сетах получается ровно набор ТЗ 6.3, при другой длине встречи — полный набор исходов
- Из консоли **не импортируется ничего из публичных фич** (ADR-004). Поэтому у неё своя таблица группы — с матрицей «каждый с каждим» и рейтингом рядом с фамилией, как требует ТЗ 6.6
- Чанки консоли — около 2 КБ gzip поверх общего бандла: до бюджета 400 КБ (ТС 8.1) далеко
- **Равенство очков спрашивается только у доигранной группы.** До этого панель висела с первой секунды турнира: пока не сыграно ничего, по нулям стоят все, и равенство есть у всех со всеми. Хуже шума было другое — решение, принятое рано, пишется в журнал `TieDecision` (ADR-008) и способно зафиксировать места по выбору, сделанному до половины группы. Найдено 03.09.2026 при проверке консоли на телефоне
- **Проверено на экране 390×844 (03.09.2026):** консоль держится без горизонтальной прокрутки — столы, очередь, ввод счёта, панель равенства и таблица «каждый с каждым» помещаются в ширину телефона. Критерий готовности MVP «судья ведёт турнир с телефона, не с ноутбука» по вёрстке выполнен; остаётся полевая проверка в зале

### Что стоит знать про второй экран

- **Транспорт — SSE, а не вебсокет** (ADR-025). Новых зависимостей не потребовалось, переподключение берёт на себя `EventSource`, а через Caddy поток идёт обычным `/api/*`. Правило `/ws/*` в `Caddyfile` осталось неиспользованным и не удалено: следующий кандидат на двусторонний канал — синхронизация офлайна
- **Шина изменений живёт в памяти процесса.** При нескольких экземплярах API экран, подключённый к одному, не увидит событий другого. Пока экземпляр один, это верно; дальше — публикация через Redis
- Событие `state` несёт состояние целиком, диффов нет. `ping` раз в 25 секунд не даёт посредникам закрыть молчащее соединение: между встречами в зале пауза измеряется минутами
- Оповещение шины идёт **после транзакции**: разбуженный раньше коммита экран перечитал бы базу и увидел состояние без только что введённого счёта
- **Столы и очередь считает клиент** теми же `buildQueue` и `buildTables`, что и консоль. Готовая очередь в ответе означала бы второе правило вызова пар — на сервере, где никто не сверит его с тем, что видит судья
- Журнала рейтинга в ответе нет намеренно: ссылка висит на стене и открывается кому угодно. Черновик по токену тоже не отдаётся — токен есть с создания турнира, а показывать до жеребьёвки нечего
- Экран сначала делает обычный `GET` и только потом открывает поток: поток отвечает потоком и на неизвестный токен, и отличить «нет такого турнира» от «сеть отвалилась» по нему нельзя
- Обрыв связи не гасит стену: остаётся последнее состояние с меткой «нет связи» и временем сборки. Турнир в зале идёт дальше, и пустой экран хуже устаревшего
- Экран **онлайновый**. Локальный режим (ОВ-4) — вместе с офлайном консоли: телевизор подключается кабелем к устройству судьи, и снимок берётся оттуда, а не с сервера

### Что стоит знать про офлайн-синхронизацию

- **Операции применяются теми же методами сервисов, что и онлайн-маршруты.** `MATCH_RESULT` идёт через тот же ввод счёта, что и запрос по сети. Второго описания правил в системе нет — запрет №2 брифа
- **Конфликт решает порядок, а не сессия судьи** (ADR-026). `RefereeSession` из ТС 6.3 убран: захват турнира одним устройством мешал бы второму судье на соседних столах
- Журнал `SyncOperation` пишется **до** применения операции. Прерванная попытка (запись есть, исхода нет) применяется заново: все шесть типов задают состояние, а не приращение
- Отклонённая операция не останавливает пачку. Отказы приходят списком `rejected`, снимок — всегда, даже на пустую пачку: синхронизация по таймеру идёт и тогда, когда судья ничего не вводил
- **`TIE_DECISION` добавлен в перечень ТС 6.2.** Без него групповой этап в зале без сети не закрыть (ADR-008), а ТЗ 6.4 требует провести турнир целиком без интернета
- `Tournament.version` растёт на каждое изменение, которое видит консоль. По нему консоль, вернувшаяся из офлайна, узнаёт, что снимок устарел
- `lastServerVersion` ничего не блокирует: она пишется в журнал и отвечает, против какого состояния судья вводил операцию
- **Дефект прав, вскрытый этой задачей:** решение по равенству требует роли владельца или организатора, а ввод счёта разрешён и судье. Судья, работавший офлайн, получит на `TIE_DECISION` отказ `FORBIDDEN` — так же, как и онлайн. ADR-008 говорит, что равенство разрешает судья. Расхождение существовало до синхронизации; чинить его — отдельное решение
- **Проверено на живой базе 02.09.2026:** турнир от создания до старта, пачка из трёх операций в перепутанном порядке — применились по `seq`; версия выросла с 2 до 5; повторная отправка той же пачки ничего не изменила

### Что стоит знать про офлайн-консоль

- **Путь действия один и в зале с сетью, и без неё:** экран меняется сразу, операция ложится в очередь на диск, очередь уходит на сервер сама. Прямых запросов на ввод счёта, назначение стола и отмену у консоли больше нет вовсе — иначе офлайн оказался бы режимом, который впервые проверяется в бою
- **На диске лежит последнее известное состояние сервера, а очередь хранит то, чего сервер ещё не видел.** Экран показывает их сумму. Локальные действия в снимок не пишутся: инвариант проще и восстанавливается после перезагрузки точно (ADR-027)
- **Снимок хранится целиком**, двумя таблицами вместо пяти: `snapshots` и `outbox`. ТС 6.2 исправлена — ADR-027
- Ответ синхронизации заменяет снимок, но поверх него накладывается всё, что ещё не отправлено: иначе счёт, введённый в момент отправки, исчез бы с экрана
- Отправка идёт по трём поводам одной функцией — возврат сети, таймер в 15 секунд, кнопка судьи (ТС 6.3). Расходиться им незачем
- **Отклонённая операция не повторяется:** сервер уже сказал, что она не ложится на состояние турнира. Она остаётся видимой судье с кодом отказа, пока он её не уберёт
- Завершение турнира — единственное действие консоли, которому нужна сеть: рейтинг считает сервер. Кнопка заблокирована, пока очередь не ушла, — иначе сервер закрывал бы турнир, не видя половины результатов
- **Precache и бюджет закреплены тестом** (ADR-032): `src/app/precache.test.ts` сам собирает приложение и проверяет, что каждый чанк из замыкания консоли лежит в манифесте Workbox. Состав берётся из манифеста сборки, а не из имён файлов: страница проведения турнира собирается в `_tournamentId-*.js`, и фильтр по имени её не видел
- Набор консоли — 183 КБ gzip при бюджете 400 КБ (ТС 8.1). В него входит общий чанк приложения, без которого консоль не откроется; сами чанки консоли весят около 38 КБ
- **Не сделано:** полевые испытания на живом турнире с выключенным Wi-Fi (ТС 9, спринт 4)

### Что стоит знать про профиль игрока

- **График рисуется своим SVG, библиотеки графиков в проекте нет** (ADR-028). ТС 2.2 исправлена. Геометрия вынесена в чистую функцию `rating-scale.ts` и проверена без DOM: ровная кривая даёт нулевой размах, а `NaN` в координате гасит **весь** график молча — на экране это пустое место, а не ошибка
- Ось времени, а не номера турнира: перерыв в полгода — часть динамики игрока, и равномерная раскладка его бы скрыла
- **Подписи границ кривой берутся из `ratingAfter` крайних точек**, а не из вычисленных границ масштаба. В число разбирается только пиксельная координата; всё, что видит человек, остаётся строкой как пришло (ADR-014)
- Холст скрыт от чтения с экрана, доступной заменой служит список турниров под ним — те же числа текстом. Убрав список, мы оставим часть людей без содержимого графика
- **Мест в истории турниров нет намеренно** — их считает движок по всему турниру (ADR-023). Строка ведёт на страницу результатов, где место показано
- Личный счёт запрашивается только по выбранному сопернику и стоит **над** историей встреч: это ответ на только что заданный вопрос, и внизу страницы его пришлось бы искать
- Три запроса, а не один: карточка, кривая и встречи живут по-разному — встречи листаются, кривая приходит целиком
- **Фамилия в таблице рейтинга стала ссылкой на профиль.** До этой задачи ссылок на профиль не было ни на одном экране: маршрут был заглушкой
- **Статистики и фильтров истории встреч нет** — ни того, ни другого нет в контракте ТС 7.2. Посчитать по видимой странице значило бы показать число, меняющееся от перелистывания. Записано как ОВ-19
- Живые ответы всех трёх маршрутов сверены со схемами контракта 02.09.2026: расхождений нет
- Казахские строки написаны агентом и носителем языка не сверялись

### Что стоит знать про кабинет

- **Кабинет — это свой профиль игрока, и только он.** Разделов ТЗ кабинету не отводит: упоминание есть лишь в V3. «Мои турниры» и «мой клуб» не выдумывались
- После входа `playerId` пуст, и до этой страницы заполнить его было нечем. Заводится профиль тем же `POST /players`, что и заведение игрока организатором: какой из двух случаев — решает сервер по наличию профиля у вошедшего (ADR-014)
- **После заведения сессия перечитывается** `GET /auth/me`, а не собирается из ответа: состав пользователя задаёт ТС 7.1. Без этого кабинет предлагал бы завести профиль, который уже есть
- Одна форма и на заведение, и на правку: `updatePlayerSchema` — это `partial` от `createPlayerSchema`, полностью заполненный он принимает. Две формы означали бы два места, где список полей обязан совпадать
- Пустое необязательное поле уходит как «не задано», а не пустой строкой: `z.string().min(1)` отвергла бы её
- **Пол в ответе — строка, а не перечень** (ТС 7.2). При правке незнакомое значение не подставляется в форму молча: человек выберет сам
- Страница читает сессию из хранилища, а не из контекста роутера: контекст — копия для `beforeLoad`, где хуков нет, и он не обновится от того, что человек завёл себе профиль. Guard'ы читают контекст, компоненты — хранилище
- **Трёх полей ТЗ 2.2 нет и не может быть без решения:** фото (маршрута загрузки файлов нет ни одного, MinIO поднят, API к нему не написан), игровая рука, хват и инвентарь (колонок нет в схеме — ОВ-12). Почта из ТЗ 2.1 показывается, но не правится: маршрута изменить её в ТС 7.1 нет
- **Проверено на живой базе 02.09.2026:** вход по коду новым номером, `playerId` пуст, `POST /players` тем же телом, что шлёт форма, — профиль заведён со стартовым рейтингом 250 и провизорностью, `GET /auth/me` сразу отдаёт `playerId`. Правка `PATCH` прошла вместе с необязательным отчеством. В базе от прогона остались пользователь `+77015550199` и его игрок: маршрута удаления игрока в контракте нет

### Что стоит знать про запись на турнир

- **Правило допуска переехало в общий код** — `@kttf/shared/eligibility`, третий чистый пакет рядом с `rating` и `brackets` (ADR-029). ADR-тест чистоты перечисляет теперь три модуля
- **Перенос доведён до конца 02.09.2026.** Копии в `kttf-back` больше нет: сервис импортирует `@kttf/shared/eligibility`, тест уехал вместе с модулем. Страница гасит кнопку записи заранее и называет причину — правило на экране и на сервере теперь буквально одно
- Пока свой профиль не прочитан, кнопка занята, а не погашена: неизвестно ещё не значит «нельзя». Профиль читается ради допуска отдельным запросом — в сессии лежит только `playerId` (ТС 7.1), а правилу нужны рейтинг, год рождения и пол
- **Планка в правило идёт числом, а `null` остаётся `null`.** `Number(null)` — это ноль, то есть планка «не ниже нуля» вместо её отсутствия; на этом стоит отдельный тест. На экране планка остаётся строкой, как пришла (ADR-014)
- Отказ сервера показывается по-прежнему: право проверяет он, интерфейс лишь не обещает того, что заведомо не сбудется. Перевод причин в тексты — одно место на оба случая
- Панель организатора допуск заранее **не** считает: добавляемого игрока она берёт из поиска, и это отдельный сценарий (ТЗ 4.3, право клуба-хозяина). Отказ там по-прежнему приходит от сервера
- Причины недопуска приходят списком в `details.problems` — все сразу, а не первая. Общий текст `VALIDATION_FAILED` («проверьте заполненные поля») здесь не годится: человек ничего не заполнял, он не проходит по планке
- Условия допуска показываются **до** нажатия (ТЗ 4.3, шаг 1). Незаданное ограничение не строкой «без ограничения», а отсутствием строки
- Интерфейс не показывает кнопку там, где отказ предрешён: гостю — вход, вошедшему без профиля — кабинет, после дедлайна — «запись закрыта». Правилом это не подменяет, право проверяет сервер
- **Запись себя и запись чужого — один маршрут.** Без `playerId` в теле человек записывает себя, с ним — организатор клуба-хозяина (ADR-014). Судья не управляет составом
- Отмена своей записи — до дедлайна; после него снимает организатор. Удалить запись можно только до старта: после него участник снимается, а не исчезает, его встречи уже в таблице (ADR-009)
- **Результаты показываются только у начатого турнира.** До старта места «не определены» у всех, а изменения рейтинга нулевые: такие таблицы выглядят поломкой, а не пустотой
- Заведение нового игрока прямо из формы турнира (ТЗ 4.3) не сделано: форма профиля живёт в кабинете, и второй её экземпляр означал бы два места, где список полей обязан совпадать
- **Проверено на живой базе 02.09.2026:** заведён клуб и турнир с планкой 400 и лимитом 16, открыта регистрация, запись прошла из интерфейса — «мест занято 1 / 16», состав и панель организатора на месте

### Что стоит знать про создание турнира

- **Вход в создание стоит на календаре турниров, а не в кабинете.** Разделов ТЗ кабинету не отводит, и «мои турниры» по-прежнему не выдумываются: кнопка появляется там, где организатор и так смотрит турниры. Видна она владельцу и организатору клуба, судье — нет (ТЗ 1)
- **Схему правит редактор над `formatConfig`, второй модели настроек нет** (ADR-024). Форма держит плоский черновик всех схем сразу, чтобы переключение не теряло введённое, и переводит его в конфигурацию контракта одной функцией `toFormatConfig`
- **Предпросчёт считает движок**, а не форма: `splitIntoGroups`, `countRoundRobinMatches`, `countRounds`, `buildKnockout`. Своя формула разошлась бы с настоящей жеребьёвкой молча, а организатор принимает решение по числу «получится 32 встречи»
- Число участников в предпросчёте — **предположение, а не настройка**: турнир заводится до записи. Оно никуда не сохраняется
- Предупреждение «из групп выходит меньше двух» — та же проверка, которой жеребьёвка отвергает конфигурацию. Здесь она предупреждение, а не отказ: настоящее число участников выяснится к жеребьёвке
- **`finalGroupCount` у человека не спрашивается:** у «финалов по местам» финальных групп ровно столько, сколько выходит из группы, и это проверяет схема. Поле с предопределённым значением — лишний повод ошибиться. Утешительной сетки в выборе нет по той же причине
- **«Повторить прошлый» копирует сервер** маршрутом `duplicate`, а не форма. Собрать тело создания из прочитанного турнира означало бы второе место со списком всех полей
- **Найден и закрыт дефект охраны маршрутов.** Роутер заводился до восстановления сессии, и его контекст с `session: null` доходил до первого сопоставления: вошедший человек, открывший **прямую ссылку** на кабинет, попадал на страницу входа. Переходом внутри приложения тот же кабинет открывался, поэтому дефект и дожил до сих пор. Роутер теперь создаётся после восстановления
- **Осторожно при живой проверке:** обновление по требованию (ADR-004) означает, что уже открытый профиль браузера продолжает получать **прошлую сборку** от работника службы. Правка, которой «не видно» после пересборки образа, — почти всегда это. Проверять на чистом профиле
- **Проверено на живом стеке 02.09.2026:** турнир заведён из формы через `https://localhost`, схема «группы и сетка» с предпросчётом «4 × 4, 4, 4, 4, встреч в группах 24, выходит 8, сетка 8, всего 32», в базе легли и `formatConfig`, и `seedingConfig`. Пробный турнир удалён

### Что стоит знать про проведение турнира

- **Дыра, найденная 02.09.2026:** во фронтенде не было ни одного действия жизненного цикла — ни публикации, ни открытия и закрытия записи, ни жеребьёвки, ни старта. Турнир создавался в статусе `DRAFT` и из интерфейса из него не выходил: организатор не доводил свой турнир даже до записи без `curl`. Маршруты (ТС 7.5) и сервер были готовы с самого начала — не было кнопок
- **Панель показывается только владельцу и организатору клуба-хозяина** (ADR-014) и стоит на странице турнира, сразу под карточкой. Отдельного «кабинета организатора» по-прежнему не выдумывается: турнир ведут там, где на него смотрят
- **Условия сверх статуса проверяет сервер, а не экран.** Старт без жеребьёвки и завершение с несыгранными встречами отвергает он; кнопки лишь не предлагают того, чего в этом состоянии не бывает вовсе. Таблица переходов на клиенте не переписана — там ответ на другой вопрос, какие кнопки показать
- **Завершение турнира отсюда не выходит:** его делает консоль, когда сыграна последняя встреча (ТЗ 6.3). У панели остаётся повтор обсчёта для турнира, застрявшего в «Завершён» из-за неудавшегося расчёта рейтинга
- **Отмена спрашивает подтверждение** и не показывается у обсчитанного турнира: рейтинг уже разошёлся по журналу событий и профилям, отмена его не вернёт (ТЗ 4.1)
- **Расстановка после жеребьёвки видна организатору до старта** — состав групп и сетка тем же `ResultsBracket`, что и после турнира. Публичные результаты показываются только у начатого турнира, и без этой врезки организатор не видел бы, кого куда развела жеребьёвка. Несведённые одноклубники (ADR-011) называются поимённо сразу после жеребьёвки
- **Обмен двумя игроками правит имена в готовых встречах, а не структуру** (ADR-033). Состав группы выводится из её встреч, а свободный проход в сетке не материализован вовсе, поэтому перестроить расстановку из базы нечем — и не нужно: размеры групп и круги сетки остаются теми, что построил движок. Игрок, обменянный с тем, кто проход занимал, получает проход сам
- **Обмен разрешён только в `REG_CLOSED`** — после жеребьёвки и до старта. Несведённые одноклубники после обмена пересчитываются тем же кодом движка, что и при жеребьёвке: `findClubCollisions` выведен из `splitIntoGroups` наружу
- **Проверено на живом стеке 02.09.2026:** пробный турнир проведён из браузера от черновика до «Идёт» — публикация, открытие записи, закрытие, жеребьёвка круговой на четверых (6 встреч), старт, появление ссылки на консоль. Статусы сверены в базе на каждом шаге. Пробный турнир и его записи удалены, «Открытый турнир Астаны» не тронут

### Что стоит знать про схему проведения

- **`groupRounds` со значением по умолчанию, а не обязательный.** Турниры, созданные до появления поля, лежат в базе без него и обязаны читаться дальше: один круг — то, как они и разыгрывались. Обязательное поле сломало бы чтение существующих строк, а не только создание новых
- У схемы «группы + финальные группы» **одно поле на оба этапа**, ровно как `setsToWin`. Отдельного параметра для финальных групп ТЗ 5.2 не задаёт, и выдумывать его не за что. Если владелец хочет разное число кругов — это новое поле и новое решение
- **Утешительную сетку отвергает схема конфигурации**, то есть маршрут создания и правки. Ответ приходит с путём `formatConfig.consolation` и человеческим текстом, а не общим «проверьте поля»
- Проверка в жеребьёвке осталась вторым рубежом: она недостижима, пока запрет стоит в схеме, и понадобится ровно в тот день, когда запрет снимут раньше, чем появится построитель
- **Проверено на живом стеке 02.09.2026:** создание с `consolation: true` отвергнуто с указанием поля, турнир с `groupRounds: 2` создан и прочитан обратно, пробный турнир удалён

### Что стоит знать про стек в Docker

- **`docker compose up -d` поднимает продукт целиком**, включая схему БД. Профиль остался один — `observability`, и он локально не нужен
- Схему накатывает разовый контейнер `kttf-migrate`, а не API при старте (ADR-030): при двух копиях приложения миграция обязана пройти один раз, а её отказ — читаться отдельно от отказа приложения
- **`Dockerfile` бэкенда многостадийный.** Прод-зависимости ставятся с нуля, а не `pnpm prune` поверх собранных: prune чистит только верхний уровень, а виртуальное хранилище `.pnpm` оставляет как было
- Две неочевидности сборки, найденные и закрытые: `prisma generate` требует `DATABASE_URL` даже без обращения к базе (передаётся заглушкой через ARG, в образе не остаётся) и **читает `tsconfig.json`, выбирая расширение в импортах клиента** — без него получается `./enums.ts`, и Node такой импорт не разрешает
- Статику отдаёт Caddy, тот же образ, что и на входе (ADR-031). `index.html` и `sw.js` — с `no-cache`: закешированный работник службы означал бы судью, до которого обновление по требованию так и не дошло
- **`NODE_ENV=production` стек теперь поднимется:** запрет держался на логовом отправителе кода, которого больше нет (ADR-034). Прод не проверялся ничем, кроме этого запрета, — перед выкаткой смотреть заново
- **Проверено 02.09.2026:** стек поднят одной командой, живой турнир открывается через прокси на `https://localhost`, миграции с нуля дают 19 таблиц на пустой базе

**ОВ-15. Кто падает в нижнюю сетку.** Владелец продукта потребовал возможность подняться из нижней сетки и играть за третье место (ТЗ 5.2). Финал нижней сетки и есть матч за третье — это согласовано. Не решено, кто в неё попадает: **все проигравшие в основной сетке** либо **только проигравшие будущим финалистам** (классический репешаж). Первое проще, предсказуемо по числу встреч и даёт игру тому, кто проиграл первую встречу и иначе уехал бы домой; второе экономит время зала, но объясняется игроку тяжелее. Блокирует построитель нижней сетки. Рекомендация агента — первое.

**ОВ-16. Правило сравнения игроков из разных групп.** ТЗ 6.7 записано по вторичным описаниям практики ITTF: отношения выигранных встреч, затем сетов, затем мячей. Первоисточник — справочник ITTF для судей — не сверялся, PDF не разобрался. **Требует подтверждения до реализации:** цена ошибки — неверно отобранные в плей-офф. Блокирует добор до размера сетки.

**ОВ-17. Колонка `Match.setsToWin`.** Длина встречи, меняющаяся к концовке (ТЗ 5.2), делает носителем этого значения саму встречу, а не конфигурацию этапа: счёт проверяется в офлайн-консоли без сети, и длина обязана лежать в снимке рядом со встречей. Требуется изменение схемы БД и миграция. Схему без решения владельца не меняем — бриф 4.1. Обоснование — ADR-024.

**ОВ-18. Фильтры публичных списков, которых нет в контракте.** ТЗ 9.1 требует фильтровать рейтинг по полу и возрастной категории, ТЗ 9.2 — календарь по планке рейтинга и возрасту. В запросах ТС 7.2 и ТС 7.5 этих полей нет: у игроков есть `search`, `city`, `clubId`, у турниров — `city`, `clubId`, `status`, `from`, `to`. Экраны сделаны на имеющихся фильтрах, самовольно контракт не расширялся (бриф 4.2). Решение за владельцем: добавить поля в схемы запросов и в выборку — или убрать требование из ТЗ. Правка затрагивает три репозитория сразу: схему в общем коде, `where` в сервисе, форму на экране. Блокирует полноту ТЗ 9.1 и 9.2, остальное работает.

**ОВ-19. Статистика игрока и фильтры истории встреч, которых нет в контракте.** ТЗ 9.3 требует на профиле блок «винрейт, средний счёт, любимый соперник, серии» и историю встреч **с фильтрами**. В контракте ТС 7.2 нет ни того, ни другого: `playerMatchesQuerySchema` — это ровно постраничность, а статистики нет ни одним полем ни в одном ответе. Посчитать это на клиенте нельзя: история отдаётся страницами, и винрейт по видимой странице менялся бы от перелистывания — ровно та причина, по которой личный счёт считает сервер (комментарий в `player-history.ts`). Решение за владельцем: завести `GET /players/:id/stats` и фильтры в запросе встреч — или убрать требование из ТЗ. Правка затрагивает три репозитория сразу, как и ОВ-18. Блокирует полноту ТЗ 9.3; страница работает, кривая, история и личный счёт на месте.

**ОВ-20. Загрузки файлов нет ни одним маршрутом.** MinIO поднят в `kttf-infra` с первого дня, а в контракте ТС 7 нет ни одного маршрута загрузки. При этом три поля ждут ссылки: `Player.photoUrl` (фото игрока, ТЗ 2.2), `Club.logoUrl` (ТЗ 3.1), фото зала (ТЗ 3.1). Форма профиля поэтому фото не спрашивает: предлагать человеку вставить ссылку на картинку — не то, что имелось в виду в требовании. Решение за владельцем: заводить ли загрузку в MVP. Технически это маршрут выдачи предподписанной ссылки плюс правило на тип и размер файла. Блокирует фото и логотипы целиком; всё остальное работает.

**Закрыт 30.08.2026 — ОВ-10 о Zod в общем коде.** Zod подключается peer-зависимостью, ADR-тест переписывается на проверку импортов `rating` и `brackets`. Решение владельца продукта, обоснование и последствия — ADR-015. Реализация не выполнена: это следующая задача, раздел 5.

**Закрыт 29.08.2026 — ОВ-8 об ограничении стадии.** Разработка продолжается за пределами спринта 1, не дожидаясь подтверждения трёх рыночных гипотез. Решение владельца продукта, принято после того, как ограничение из раздела 9 было названо.

**Закрыт 29.08.2026 — ОВ-7 о видимости репозиториев.** Все три репозитория остаются **публичными**, включая `docs/01-context.md` с финансовой моделью, разбором монетизации конкурента и тактикой захода на клубы. Решение владельца продукта, принято после того, как риск был назван. Переоткрывать не нужно; если позже потребуется закрыть — учитывать, что публикация уже состоялась и отзыву не подлежит.

## 9. Ограничение стадии

По `00-README.md` три рыночные гипотезы не подтверждены: готовность игроков потерять рейтинг конкурента, модель оплаты конкурента в РК, готовность клубов проводить больше мелких турниров.

**Ограничение снято владельцем продукта 29.08.2026 — ОВ-8.** Разработка идёт дальше спринта 1, не дожидаясь подтверждения. Раздел оставлен, потому что риск никуда не делся: если гипотезы не подтвердятся, переделке подлежит всё, кроме `rating` и `brackets`. Эти два от исхода не зависят — формула и генерация сеток нужны при любом.

**Что по-прежнему ждёт.** Оплата и раскатка на клубы: они упираются прямо в непроверенные гипотезы, а не в готовность кода.
