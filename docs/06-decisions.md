# 06. Журнал решений (ADR)

_Принятые решения и их обоснование. Записи не удаляются: отменённое помечается `ЗАМЕНЕНО НА ADR-NNN` и остаётся, чтобы причина не открывалась заново._

**Формат записи:** контекст → решение → обоснование → последствия.

Новая запись добавляется, когда решение влияет на архитектуру, формулу рейтинга, модель данных или контракт API. Мелкие реализационные развилки сюда не идут.

## ADR-001. Три репозитория: приложения раздельно, общий код в kttf-shared

**Дата:** 29.08.2026
**Статус:** принято
**Заменяет:** промежуточное решение о монорепозитории на pnpm workspaces

**Контекст.** Первая редакция ТС описывала монорепозиторий с `apps/{api,web,console}`. Промежуточно он был собран на `pnpm workspaces`, но владелец продукта завёл на GitHub три отдельных репозитория и потребовал, чтобы на верхнем уровне не было ничего, кроме проектов, — в том числе `node_modules`.

Требование однозначно определяет архитектуру: корневой `node_modules` неустраним при воркспейсе, потому что там живёт виртуальный стор pnpm. Нет корневого `node_modules` — нет и воркспейса.

**Решение.** Три независимых репозитория, лежащих рядом:

| Репозиторий   | Что внутри                                                                                                    |
| ------------- | ------------------------------------------------------------------------------------------------------------- |
| `kttf-back`   | NestJS API                                                                                                    |
| `kttf-front`  | React PWA, включая модуль консоли судьи (ADR-004)                                                             |
| `kttf-shared` | Всё общее: движок рейтинга, генерация сеток, типы, конфигурация линтера и TypeScript, документация, ADR-тесты |

Новое приложение — новый репозиторий. Верхний уровень содержит только папки проектов.

**Документация и `CLAUDE.md` живут в `kttf-shared`.** Это единственный репозиторий, от которого зависят оба приложения, поэтому контекст едет вместе с ним и доступен агенту на любой машине.

**Обоснование.** Решение владельца продукта.

**Чем платим — и как это закрыто.** Общий код перестал быть частью одного дерева, поэтому `workspace:*` больше не действует: приложения подключают `kttf-shared` как git-зависимость. Отсюда риск, прямо задевающий запрет №2 брифа: бэкенд и фронтенд могут разъехаться по версиям движка, и офлайн-консоль посчитает таблицу иначе, чем сервер. Причём тихо.

Обязательная мера: **git-зависимость закрепляется коммитом, а не веткой.** Оба приложения обязаны ссылаться на один и тот же SHA, и обновляются они одной парой синхронных правок. Ветка вместо SHA означает, что версии разъедутся при первом же независимом `pnpm install`.

**Последствия.**

- Корневые `package.json`, `pnpm-workspace.yaml`, `node_modules` удалены. Верхний уровень — три папки
- У каждого репозитория свой `node_modules`, свои скрипты, свой CI
- `kttf-shared` экспортирует не только код, но и конфигурацию: `./config/tsconfig.base.json`, `./config/eslint`, `./config/prettier`. Приложения не заводят свои копии правил
- ADR-тесты, проверяющие раскладку соседних репозиториев, пропускаются, когда выкачан один репозиторий. В CI это норма, а не провал
- Turborepo не используется: оркестрировать нечего, у каждого репозитория свои команды

## ADR-002. Формула конкурента RTTF изучена по первоисточнику

**Дата:** 29.08.2026
**Статус:** принято, справочное

**Контекст.** `01-context.md` содержал формулу RTTF по пересказу. Перед проектированием собственной формулы требовался первоисточник.

**Что установлено** ([правила RTTF](https://rttf.ru/content/2), [описание рейтинга](https://rttf.ru/content/24), [критика формулы ФНТР](https://rttf.ru/content/91)):

```
Δ = [(100 − (R_победителя − R_проигравшего)) / 10] × k × D
```

| Элемент                          | Значение                                                                                                                                   |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Разрыв ≥ 100 в пользу победителя | **Δ = 0** — сильный не получает ничего за победу над слабым                                                                                |
| `k` — коэффициент турнира        | Выводится из **среднего рейтинга участников**: 0.2 при Rср < 250, далее 0.25 / 0.3 / 0.35, 0.4 при Rср > 550. Организатором не назначается |
| `D` — коэффициент счёта          | 0.8 при разнице в 1 сет, 1.0 при 2 сетах, 1.2 при 3+                                                                                       |
| Новичок (сыграл ≤ 5 турниров)    | Всегда `D = 1`; `k = 1` при победе, `k = 0.5` при поражении — **асимметрия намеренная**                                                    |
| Стартовый рейтинг                | Назначается организатором, кратен 25, минимум 100                                                                                          |
| Минимум                          | Рейтинг не опускается ниже 1                                                                                                               |

**Три вывода, повлиявших на нашу формулу:**

1. **RTTF считает одну дельту на встречу и применяет её симметрично.** Замкнутость у них — свойство конструкции, а не отдельное правило.
2. **Замкнутость для них — главный аргумент.** Формулу ФНТР они отвергают именно за инфляцию: победитель получает вдвое больше, чем теряет проигравший. Экспериментальный пересчёт всей истории RTTF с 2011 года по формуле ФНТР поднял рейтинги активных игроков примерно вдвое, и рейтинг перестал отражать силу игры.
3. **Даже они нарушают замкнутость для новичков — сознательно.** Асимметрия `k = 1 / 0.5` существует, чтобы новичок быстро дошёл до реальной силы. Ограничена коротким окном.

**Последствия.** Пункты 1 и 3 напрямую разрешили противоречие в нашей формуле (ADR-003). Пункт по `k` от среднего рейтинга поставлен открытым вопросом ОВ-1.

## ADR-003. Формула рейтинга 2.0

**Дата:** 29.08.2026
**Статус:** принято
**Заменяет:** формулу версии 1.0 из первой редакции `02-requirements.md`, раздел 7

**Контекст — что было сломано.** Версия 1.0 требовала одновременно двух несовместимых вещей:

- ТЗ 7.2: «Δ проигравшего равен −Δ победителя (система замкнута)», продублировано инвариантом №1 в брифе
- ТЗ 7.2: коэффициент `K` задан **для каждого игрока отдельно** (провизорный 40, R < 300 → 25, R < 500 → 20, R ≥ 500 → 15), и `RatingOutput` в ТС возвращал `kFactorA` и `kFactorB` раздельно

Провизорный новичок (`K = 40`) против игрока с R ≥ 500 (`K = 15`) даёт `40 × ... ≠ −15 × ...`. Замкнутость арифметически недостижима. Инвариант №1 не мог быть выполнен ни при какой реализации.

**Решение.**

1. **Одна дельта на встречу, применяется симметрично.** Базовая величина считается один раз, `K` умножается на неё отдельно для каждого игрока. Когда оба игрока рейтинговые, `K` совпадает и дельты в точности противоположны — замкнутость обеспечена конструкцией.
2. **Градация `K` по уровню рейтинга (25 / 20 / 15) удалена.** Заменена единой `K_BASE = 20`.
3. **Добавлен множитель разрыва `G = max(0, 1 − max(0, gap) / 100)`.** При разрыве 100 и более в пользу победителя рейтинг не меняется ни у кого.
4. **Провизорный период — единственное место, где замкнутость нарушается**, и нарушается намеренно: `K_PROV_WIN = 40`, `K_PROV_LOSS = 20`. Расхождение не прячется: возвращается явным полем `imbalance` и отслеживается метрикой инфляции (ТС 5.6).
5. **Рейтинги фиксируются на момент старта турнира.**

**Обоснование по пунктам.**

_Почему удалена градация `K`._ Она и есть источник противоречия. Роль, которую она играла — низкорейтинговые двигаются быстрее — полностью закрыта провизорным периодом (новые игроки) и множителем `G` (мисматчи). У конкурента градации по рейтингу игрока нет вовсе, и его рейтинг работает 18 лет.

_Почему множитель разрыва именно такой._ Требование владельца продукта: при разрыве более 100 очков рейтинг не забирать вовсе. Это же правило действует у конкурента, игроки к нему привыкли, и оно содержательно верно — победа над заведомо более слабым не является информацией о силе игрока. Линейное затухание выбрано вместо жёсткой отсечки, чтобы функция была **непрерывной**: у отметки 100 нет скачка, эффект плавно уходит в ноль, порога для «парковки» не возникает. У конкурента непрерывность получается сама собой, потому что его формула линейна по разрыву; у нас она добавлена явным множителем поверх логистической шкалы Эло.

_Почему провизорная асимметрия допустима._ Так делает конкурент, который отвергает формулу ФНТР именно за инфляцию — то есть допускает её осознанно, а не по недосмотру. Вброс ограничен по построению: не более 20 встреч на игрока за всё время существования аккаунта. Ключевое отличие от ФНТР: там асимметрия действует **на каждой встрече каждого игрока всегда**, у нас — в коротком окне и только у новичков.

_Почему рейтинги фиксируются на старте турнира._ Без фиксации результат зависит от порядка обработки встреч: одна и та же сетка даёт разный итог при разной последовательности ввода счёта. Для офлайна это фатально — консоль обязана посчитать локально ровно то же, что сервер. Плюс расчёт становится идемпотентным и параллелизуемым.

**Чего решение не делает.** Формула не защищает от сдачи игр. Игрок с рейтингом 520, проигравший игроку с 300, теряет около 18 пунктов, и отличить сданную встречу от честного поражения формула не может — да и не должна, потому что честное поражение такому сопернику действительно означает завышенный рейтинг. Правило `G = 0` убирает только выгоду от **набивания** рейтинга на слабых. Сдача игр закрывается обнаружением аномалий и человеком (ТЗ 7.7), и утверждать иначе — вводить себя в заблуждение.

**Последствия.**

- `02-requirements.md` раздел 7 и `03-tech-spec.md` раздел 5 переписаны
- Инвариант №1 брифа (`deltaA === -deltaB` для любых входных данных) **более не верен в этой формулировке**. Заменён на «замкнутость для пар рейтинговых игроков» + «`imbalance` ненулевой тогда и только тогда, когда хотя бы один игрок провизорный». `04-agent-brief.md` раздел 5.2 обновлён
- Требуются поля `Registration.ratingAtStart` и `Registration.matchesAtStart` (см. `05-state.md`, раздел 6)
- Константы подлежат калибровке на реальных протоколах (ОВ-3)
- Коэффициент турнира остаётся объявляемым организатором — вектор манипуляции, вынесен в ОВ-1

## ADR-004. Фронтенд единый, консоль — модуль внутри него

**Дата:** 29.08.2026
**Статус:** принято
**Уточняет:** ADR-001

**Контекст.** `03-tech-spec.md` раздел 3 в первой редакции описывал три приложения: `apps/api`, `apps/web` и отдельное `apps/console` (нейминг первой редакции). Разделение обосновывалось бюджетом бандла консоли (`< 400 КБ gzip`) и изолированным service worker для офлайна.

**Решение.** Приложений два: `kttf-back` и `kttf-front`. **Фронтенд единый — один сайт, одна точка входа, одна установка PWA, одна сессия.** Консоль проведения турнира — крупный модуль `kttf-front/src/features/console/`, а не отдельное приложение.

**Обоснование.** Решение владельца продукта. Разделение на два фронтенда создавало две установки PWA и две сессии у одного человека: тренер, который проводит турниры, обычно ещё и играет. Это прямо противоречит критерию готовности MVP «организатор проводит второй турнир, не открывая инструкцию» — два приложения сами по себе требуют объяснения, какое из них для чего.

Аргумент за разделение (гарантия бюджета бандла) снимается техническими мерами, а не архитектурой: бюджет проверяется в CI.

**Последствия.**

- Маршруты консоли грузятся лениво отдельными чанками
- **Workbox precache этих чанков обязателен.** Ленивый чанк, не предзагруженный заранее, в офлайне недоступен — судья откроет консоль в зале без сети и получит пустой экран. Это самый вероятный способ сломать офлайн-режим в единой сборке, и он обязан быть закрыт тестом
- Бюджет `< 400 КБ gzip` относится к набору чанков консоли, а не ко всему приложению. Проверяется автоматически в CI, красная сборка при превышении
- Тяжёлые зависимости публичной части (`recharts`, карты) не должны попадать в чанки консоли
- `03-tech-spec.md` разделы 3 и 8.1 обновлены

## ADR-005. Инструментарий разработки

**Дата:** 29.08.2026
**Статус:** принято

**Контекст.** ТС фиксировала прикладной стек, но не называла ни линтер, ни форматтер, ни тестовый раннер. Без этого первый же коммит задаёт их по умолчанию и молча.

**Решение.**

| Задача              | Выбор                                                                |
| ------------------- | -------------------------------------------------------------------- |
| Линтер              | ESLint 9, flat config + typescript-eslint с **type-aware** правилами |
| Форматтер           | Prettier                                                             |
| Тесты               | Vitest — один раннер на все три репозитория                          |
| Рантайм             | Node.js 24 LTS                                                       |
| TypeScript          | **6.x, не 7.x** — см. ниже                                           |
| Версии зависимостей | Актуальные стабильные на момент установки, кроме TypeScript          |

**Обоснование.**

_Линтер._ Выбран ESLint, а не Biome, несмотря на скорость последнего. Причина одна и она решающая: бриф 3.1 запрещает `any` и требует `unknown` с сужением. Синтаксическая проверка ловит только явное `any` в коде. Реальный путь проникновения `any` — протекание из внешних типов, `JSON.parse`, нетипизированных библиотек, и ловится он **только** правилами с доступом к типам (`no-unsafe-assignment`, `no-unsafe-call`, `no-unsafe-member-access`, `no-unsafe-return`). Type-aware линтинга у Biome нет. Цена — медленнее и больше конфига.

_Тесты._ Vitest вместо Jest по умолчанию в NestJS: один раннер на чистые пакеты, фронт и бэк, ESM без плясок, API совместим с Jest.

_Node 24._ Текущий LTS и уже установлен на машине разработки. ТС называла 22 — обновлено.

_Версии._ Проект гринфилд, август 2026. Числа версий в ТС — ориентир, а не фиксация: тянуть заведомо устаревшее незачем. Обновление мажорной версии чего-либо ключевого фиксируется отдельной записью здесь.

_TypeScript 6, а не 7._ Обнаружено при установке. TypeScript 7.0.2 — текущий `latest`, но `typescript-eslint@8.68.0` объявляет `typescript: ">=4.8.4 <6.1.0"` и падает с `Error: typescript-eslint does not support TS 7.0`. Версии typescript-eslint под TS 7 на 29.08.2026 не существует: последняя стабильная 8.68.0, канареечная 8.68.1-alpha.6.

Выбор между «TypeScript 7 без type-aware линтинга» и «TypeScript 6 с ним» решается однозначно: type-aware линтинг — единственное обоснование, по которому в этом же ADR выбран ESLint. Отказавшись от него, мы теряем смысл выбора и контроль над запретом `any`. Компилятор при этом не страдает: TS 6.0.3 — стабильный релиз.

**Пересмотреть, когда** typescript-eslint выпустит поддержку TS 7. Тогда обновление даёт заметное ускорение проверки типов (в 7 компилятор нативный) без потерь.

**Последствия.**

- `03-tech-spec.md` дополнен разделом 2.6
- Установлен `pnpm` (в системе отсутствовал)
- TypeScript закреплён на `^6.0.3`. Обновление до 7 без проверки линтера сломает `pnpm lint`

## ADR-006. Решения проверяются тестами, а не доверием

**Дата:** 29.08.2026
**Статус:** принято

**Контекст.** Решение, записанное только в markdown, живёт до первого человека, который его не прочитал. На проекте, где значительную часть кода пишут агенты в отдельных сессиях, это не гипотетический риск: контекст между сессиями теряется по умолчанию, и следующий агент спокойно заведёт лишнюю папку на верхнем уровне, вернёт воркспейс или добавит зависимость в чистый пакет.

**Решение.** Директория `tests/` репозитория `kttf-shared` — набор тестов, проверяющих решения из этого журнала. Запускается вместе с обычными тестами (`pnpm test`).

Проверяется сейчас:

| Что                                                                           | Откуда          |
| ----------------------------------------------------------------------------- | --------------- |
| Три репозитория на месте, монорепозиторных артефактов нет                     | ADR-001         |
| Корень чистый — список разрешённых записей закрытый                           | ADR-001         |
| Третьего приложения под консоль нет, консоль внутри `kttf-front`              | ADR-004         |
| Линтер — ESLint с type-aware правилами, не Biome                              | ADR-005         |
| Node ≥ 24, пакетный менеджер pnpm                                             | ADR-005         |
| У `kttf-shared` ноль runtime-зависимостей, нет Node API, нет БД и фреймворков | Бриф, запрет №2 |
| Покрытие движка закреплено порогом 100% в конфиге и скрипте                   | Бриф 5.1        |
| Константы формулы в коде совпадают с задокументированными в ТЗ                | ADR-003         |
| `.env` под игнором                                                            | Бриф, запрет №9 |
| Файлы контекста на месте, `CLAUDE.md` обязывает их пополнять                  | —               |

**Обоснование.** Дешевле любого ревью и не зависит от того, прочитал ли кто-то документацию. Проверка констант формулы отдельно ценна: расхождение кода и ТЗ по рейтингу — ровно тот класс ошибок, который необратимо ломает доверие к продукту.

**Как читать падение такого теста.** Оно означает не «поправь код», а развилку: **либо код разошёлся с решением, либо решение устарело.** Во втором случае правится ADR и тест, и это нормальный ход — журнал живой. Ненормально молча ослабить тест, чтобы сборка позеленела.

**Последствия.**

- Каждое новое архитектурное решение сопровождается проверкой здесь, если оно проверяемо
- Список разрешённых записей на верхнем уровне закрытый: новая папка валит сборку, пока её не внесут осознанно
- Проверки раскладки соседних репозиториев пропускаются, когда выкачан один репозиторий: в CI это норма, а не провал

## ADR-007. Агент не подписывается соавтором коммитов

**Дата:** 29.08.2026
**Статус:** принято

**Контекст.** По умолчанию агент добавляет в конец сообщения коммита трейлер `Co-Authored-By` с собственным именем. На этом проекте значительную часть кода пишут агенты, поэтому такой трейлер оказался бы почти в каждом коммите.

**Решение.** **Трейлер `Co-Authored-By` с именем агента в коммиты не добавляется. Никогда.** Ни в каком виде, ни в каком репозитории проекта. Авторство коммита — человек, отправивший изменение.

**Обоснование.** Решение владельца продукта.

**Последствия.**

- Правило продублировано в `CLAUDE.md`, потому что читается оно раньше журнала решений
- Коммиты, сделанные до принятия решения, переписаны: трейлер удалён, `kttf-back` и `kttf-front` отправлены заново с перезаписью. Репозитории были созданы за минуты до этого и содержали по одному коммиту, поэтому переписывание истории никого не задело
- Требование относится только к подписи агента. Обычное соавторство между людьми трейлером `Co-Authored-By` оформляется как принято

## ADR-008. Равенство в таблице: система предлагает, судья утверждает

**Дата:** 29.08.2026
**Статус:** принято

**Контекст.** ТЗ 6.6 задаёт шесть правил разрешения равенства очков в групповой таблице. Речь не о ничьей во встрече — её не бывает, играют до N выигранных сетов. Речь о равенстве **в таблице**: в круговой на четверых и больше регулярно выходит, что двое или трое набрали поровну. Первые пять правил детерминированы, шестое — «жребий» — нет.

Чистая функция бросить жребий не может: консоль в офлайне и сервер обязаны получить одинаковые места, иначе расчёт расходится, а это необратимо ломает доверие (бриф, запрет №2).

**Решение.** Движок применяет правила 1–5 и возвращает **предложенный** порядок вместе с признаком, что равенство осталось неразрешённым и требует решения судьи. Судья подтверждает предложение одним действием или переставляет вручную. Решение сохраняется как данные, синхронизируется наравне с остальными операциями и попадает в журнал.

**Обоснование.** Решение владельца продукта: «результат предлагает система, а потом принимает решение судья руками».

Автоматический псевдожребий по хешу отвергнут: он выглядит как жребий, но им не является, и проигравшему место объяснить нечем. Настоящая жеребьёвка в зале происходит на глазах у игроков — интерфейс это отражает, а не подменяет.

**Последствия.**

- Возврат функции расчёта таблицы содержит не только места, но и перечень неразрешённых групп равенства
- Пока равенство не разрешено, турнир не может перейти в «Завершён»: места не определены
- Требуется хранение решения судьи. Поле накапливается в `05-state.md`, раздел 6
- Функция остаётся чистой и детерминированной: решение судьи приходит на вход, а не берётся изнутри

## ADR-009. Снявшийся участник в групповой таблице

**Дата:** 29.08.2026
**Статус:** принято, временное

**Контекст.** ТЗ 4.4 описывает, что делать с рейтингом снявшегося: сыгранные встречи учитываются, несыгранные засчитываются сопернику технической победой и на рейтинг не влияют. Про **таблицу и места** там не сказано ничего.

**Решение.** Тот же порядок, что для рейтинга: сыгранные встречи остаются в таблице как есть, несыгранные идут соперникам технической победой.

**Обоснование.** Решение владельца продукта: пока делаем по ТЗ 4.4, логику меняем по ходу, если практика покажет иначе.

Так таблица и рейтинг считают одно и то же, и это главное: расхождение между «местом в таблице» и «изменением рейтинга» игроки заметят сразу и объяснить его будет нечем.

**Известный изъян.** Те, кто успел сыграть со снявшимся до снятия, и те, кто получил техническую победу, оказываются в неравных условиях. Это осознанно принятая цена за совпадение с рейтингом.

**Пересмотреть**, если на реальных турнирах изъян начнёт влиять на распределение мест. Альтернативы — аннулировать все встречи снявшегося или учитывать их в зависимости от доли сыгранного (так устроены многие официальные регламенты). Обе требуют решить, что делать с уже начисленным рейтингом.

## ADR-010. Как приложения подключают общий код

**Дата:** 29.08.2026
**Статус:** принято
**Уточняет:** ADR-001

**Контекст.** ADR-001 постановил, что приложения подключают `kttf-shared` git-зависимостью, закреплённой SHA. Как именно это работает, проверено не было. Дымовой тест на `kttf-back` вскрыл две вещи, которые не видны из документации.

**Что выяснилось.**

1. **`dist` под гитигнором, а из git ставится содержимое репозитория.** Потребитель получает исходники без сборки. Нужен скрипт `prepare`, который собирает пакет на стороне потребителя при установке.
2. **pnpm 11 по умолчанию блокирует сборочные скрипты git-зависимостей.** Требуется явное разрешение в `pnpm-workspace.yaml` потребителя, и **ключ разрешения содержит полный URL тарбола вместе с SHA**. Форма без SHA не работает — проверено.

Следствие: одно обновление общего кода — это две согласованные правки в каждом приложении. Рассинхронизировать их руками легко, а ошибка установки при этом невнятная.

**Решение.**

- В `kttf-shared` добавлен скрипт `prepare`, собирающий `dist` при установке
- В каждом приложении лежит `scripts/bump-shared.mjs`: принимает SHA, правит обе точки разом и отказывается работать с веткой
- В каждом приложении лежит `scripts/check-shared.mjs`: проверяет, что пакет реально импортируется и считает верно. Запускается после каждого обновления и в CI

**Почему не стали коммитить `dist` в репозиторий.** Это убрало бы и `prepare`, и разрешение сборки — одной правкой меньше. Но появился бы класс ошибок «`dist` разошёлся с исходниками»: сборка молча отстаёт, и приложения считают рейтинг по старой формуле, ничего не сообщая. Текущий вариант при ошибке **падает громко** на установке. Для проекта, где приоритет №1 — корректность рейтинга, громкий отказ лучше тихой неверности.

**Пересмотреть**, когда появится CI: публикация в GitHub Packages с семантическими версиями снимает и разрешение сборки, и ручную синхронизацию SHA. Цена — потребителям и CI понадобится токен даже для публичного пакета.

**Дополнение 29.08.2026, по итогам первого реального обновления.** Смена SHA всегда роняет первую установку с `ERR_PNPM_IGNORED_BUILDS`: pnpm помнит предыдущий SHA как пакет с запрещённой сборкой и дописывает для него строку-заглушку в `pnpm-workspace.yaml`. Это не ошибка обновления, а его нормальный ход. Скрипт допускает отказ первой установки, убирает заглушку и ставит заново — вторая установка обязана пройти чисто, поэтому настоящая ошибка по-прежнему валит обновление.

Там же выяснилось, что разрешения сборки нельзя перезаписывать файлом целиком: в `kttf-back` рядом с общим кодом живут `prisma`, `@prisma/engines` и `esbuild`. Ключ общего кода правится на месте, соседние остаются.

**Последствия.**

- Обновление общего кода: `node scripts/bump-shared.mjs <SHA>` → `pnpm install` → `pnpm check:shared`, **в обоих приложениях одним и тем же SHA**
- Ветка вместо SHA по-прежнему запрещена, теперь ещё и технически: скрипт её не примет
- Обновление трогает только ключ `@kttf/shared`; прочие разрешения сборки переживают его

## ADR-011. Посев важнее разведения по клубам

**Дата:** 29.08.2026
**Статус:** принято

**Контекст.** ТЗ 5.2 требует от жеребьёвки двух вещей одновременно: посева по рейтингу и разведения игроков одного клуба по разным группам. В общем случае выполнить оба нельзя. Если в клубе игроков больше, чем групп, совпадение неизбежно арифметически. Если сильнейшие двое из одного клуба, развести их можно только сдвинув одного на уровень слабее.

**Решение.** **Приоритет у посева.** Разведение по клубам работает только перестановками **внутри одной полосы змейки** — то есть между игроками примерно равной силы. Полоса никогда не меняется.

Оставшиеся совпадения не замалчиваются: `splitIntoGroups` возвращает их отдельным списком с указанием клуба, группы и участников.

**Обоснование.** Сдвиг игрока через полосу делает группы неравными по силе, и это видно всем: в одной группе два фаворита, в другой ни одного. Турнир от такого страдает сильнее, чем от двух одноклубников в одной группе. К тому же неравные группы влияют на то, кто выйдет в плей-офф, — то есть на спортивный результат, а совпадение по клубу влияет только на удобство.

Список совпадений важнее автоматики: организатор видит их до старта и правит руками, если считает нужным. ТЗ 5.3 ручную корректировку уже требует.

**Алгоритм.** Жадный выбор: для каждой позиции берётся первый участник полосы, чей клуб ещё не представлен в целевой группе. Оптимума при сложных раскладах он не гарантирует, но детерминирован, а на реальных составах (12–24 участника, единицы клубов) даёт тот же результат, что полный перебор.

**Последствия.**

- `splitIntoGroups` возвращает `clubCollisions` — неразведённые совпадения
- Разведение можно выключить флагом `separateByClub: false`
- Если практика покажет, что клубы важнее равенства групп, менять придётся не алгоритм, а это решение

## ADR-012. Инфраструктура — четвёртый репозиторий

**Дата:** 29.08.2026
**Статус:** принято
**Дополняет:** ADR-001

**Контекст.** Описание стека оркеструет **оба приложения сразу**: собирает образы из `kttf-back` и `kttf-front`, связывает их с базой, очередью, хранилищем файлов и прокси. Положить его внутрь одного из приложений значит заставить это приложение знать про устройство другого.

**Решение.** Отдельный репозиторий **`kttf-infra`**. В нём `compose.yaml`, `Caddyfile`, конфигурация Prometheus и `.env.example`.

Верхний уровень теперь содержит четыре папки. Правило из ADR-001 не нарушено, а применено: новая сущность — новый репозиторий.

**Устройство стека.**

- Одна сеть `kttf-net`, подсеть `172.28.0.0/16` задана явно. Выданная Docker наугад меняется между пересозданиями, и её нельзя прописать в правилах firewall
- Сервисы общаются по именам контейнеров и штатным портам: `postgres:5432`, `redis:6379`, `minio:9000`
- Наружу открыт только прокси. Порты базы и очереди открыты дополнительно для миграций и отладки с хоста
- **Порты хоста смещены:** PostgreSQL на `5433`, Redis на `6380`. На машине разработчика уже стоит свой PostgreSQL на 5432, и конфликт выглядел бы как «база не поднялась», хотя дело в занятом порте
- Приложения и наблюдаемость убраны в профили `apps` и `observability`. Без этого `docker compose up` падал бы сегодня, пока приложений ещё нет

**Локаль базы.** PostgreSQL инициализируется с `ru-RU` через ICU. Иначе сортировка фамилий машинная: «Ё» в конце алфавита, регистр влияет на порядок. В списке участников это видно сразу. Локаль задаётся только при создании тома — смена переменной на существующей базе ничего не меняет.

**Последствия.**

- ADR-тест, проверяющий состав верхнего уровня, дополнен `kttf-infra`
- Образы приложений: локально сборка из соседних папок, в проде из GHCR по тегу
- Оверрайд для разработки не написан намеренно: он понадобится, когда появятся приложения, а сочинять его вслепую значит гадать о структуре, которой ещё нет

## ADR-013. Аутентификация без провайдера SMS

**Дата:** 29.08.2026
**Статус:** принято

**Контекст.** ТЗ 2 и ТС 7.1 задают вход по телефону и одноразовому коду. Договора с провайдером (ТС 2.5 — Mobizon, SMSC.kz) нет, и владелец продукта решил не заводить его на этой стадии — ОВ-9. Требовалось решить, что при этом делать с аутентификацией: откладывать её целиком или строить без отправки.

**Решение.** Аутентификация делается целиком, отправка кода прячется за портом `CodeSender`. Контракт ТС 7.1 не меняется: маршруты, тела запросов и ответов те же, что были бы с настоящим провайдером. Меняется только реализация одного интерфейса.

Текущий адаптер пишет код в лог приложения и **отказывается собираться при `NODE_ENV=production`**. Отказ происходит при сборке контейнера зависимостей, то есть приложение просто не поднимается.

**Обоснование запрета на продакшн.** Адаптер, пишущий код в лог, — это вход в любой аккаунт для всякого, у кого есть доступ к логам. Забыть подменить его при выкатке слишком легко, а обнаруживается такая забывчивость по факту взлома. Громкий отказ на старте дешевле.

### Что решено сверх документов

Три вещи в документах не описаны. Они приняты здесь, а не изобретены молча.

**1. Первый успешный вход заводит аккаунт.** Отдельной регистрации в ТС 7.1 нет, пароля по ТЗ 2.1 не существует, «повторный вход — снова по коду». Другого момента для создания аккаунта в контракте не остаётся. Профиль игрока при этом **не** создаётся: ТЗ 2.2 заполняется отдельным шагом, до тех пор `playerId` пуст.

**2. Состав `user` в ответе.** ТС 7.1 говорит, что `verify-code` возвращает `user`, но не говорит какой. Отдаётся только нужное сразу после входа: идентификатор, телефон, email, локаль, наличие профиля игрока, роли в клубах. Рейтинг и остальной профиль берутся запросом к 7.2 — они меняются независимо от сессии, и класть их сюда значило бы отдавать устаревшее при каждом обновлении токена.

**3. Числа, которых нет в документах.** Длина кода — 6 цифр. Попыток ввода на код — 5: без ограничения шестизначный код перебирается за время своей жизни. Время жизни access-токена — 15 минут: у JWT нет отзыва, и это граница, за которой отозванная сессия перестаёт быть опасной, а обновление ещё не происходит на каждом втором запросе. Все три собраны в `auth.constants.ts` с указанием источника у каждой — требование это или выбор.

### Хранение секретов

- **Коды** хешируются HMAC с серверным ключом, а не голым SHA-256. Шестизначных кодов миллион, таблица их хешей строится за секунды: без ключа утечка базы означала бы восстановление всех действующих кодов
- **Refresh-токены** уезжают в `Session.refreshToken` хешем SHA-256. Ключ здесь не нужен — токен содержит 256 бит случайности. **Модель данных не меняется:** колонка как была строкой с ограничением уникальности, так и осталась, но лежит в ней хеш, а не токен
- **Ключ подписи токенов и ключ хеширования кодов — разные.** Утечка одного не должна давать возможностей другого, и ротируются они по разным поводам
- Сверка кода идёт за постоянное время: обычное сравнение строк выдаёт длину совпадения

**Refresh-токен заменяется при каждом обновлении.** ТЗ 2.1 требует продления сессии при активности; заодно украденный токен перестаёт работать после первого же обновления настоящим владельцем.

**Погашение кода и создание сессии — одна транзакция.** Иначе отказ посередине оставляет либо погашенный код без входа, либо действующий код после входа.

**Последствия.**

- Подключение провайдера — это новый класс, реализующий `CodeSender`, и одна строка в `auth.module.ts`. Эндпоинты не трогаются
- Пока адаптер логовый, стенд с `NODE_ENV=production` не поднимется. Это намеренно
- `AuthCode` и `Session` растут без ограничения: уборка истёкших записей — фоновая задача, её ещё нет

## ADR-014. Права в домене клубов и игроков

**Дата:** 30.08.2026
**Статус:** принято

**Контекст.** ТС 7.2 и 7.4 задают маршруты, ТЗ 1 — роли, ТС 8.3 требует проверять роли guard'ами, а не интерфейсом. Кто именно что может, документы прямо не перечисляют: роль «Организатор» описана как «управление клубом, создание турниров», «Владелец клуба» — «всё что организатор + управление составом организаторов», «Судья» — «консоль проведения конкретного турнира».

**Решение.**

| Действие                            | Кто                                                   |
| ----------------------------------- | ----------------------------------------------------- |
| Читать клубы, игроков, состав клуба | Кто угодно, без токена                                |
| Создать клуб                        | Любой вошедший; создатель сразу становится владельцем |
| Править клуб                        | Владелец, организатор                                 |
| Вести состав клуба                  | Только владелец                                       |
| Завести игрока в клубе              | Владелец, организатор этого клуба                     |
| Править профиль игрока              | Сам игрок либо владелец или организатор его клуба     |

**Судья не управляет клубом.** По ТЗ 1 его доступ — консоль конкретного турнира. Ни правка клуба, ни заведение игроков туда не входят.

**Создатель клуба становится владельцем** в той же транзакции. Иначе клуб появляется без единого человека, который может им управлять, и назначить владельца некому. Кто вправе создавать клуб, ТЗ не оговаривает — записано как ОВ-13.

**Последнего владельца исключить нельзя.** Клуб остался бы без человека, способного назначить нового, и починить это можно было бы только руками в базе.

### Заведение игрока закрывает два случая

ТС 7.2 описывает `POST /players` как «создание организатором». Другого способа завести профиль в контракте нет, а ТЗ 2.2 требует профиль при регистрации. Маршрут закрывает оба случая, и какой именно — решает наличие профиля у вызывающего:

1. Своего профиля нет — заводится он, `userId` проставляется. Это регистрация по ТЗ 2.2
2. Свой профиль есть — заводится чужой, без аккаунта, и тогда вызывающий обязан быть владельцем или организатором указанного клуба

Расхождение с формулировкой ТС 7.2 записано как ОВ-14: либо контракт подтверждается в этом виде, либо правится текст спецификации.

**Следствие, которое стоит знать.** При саморегистрации клуб берётся из тела запроса без проверки: игрок объявляет свою принадлежность сам, как и предусматривает ТЗ 2.2, где клуб перечислен среди полей профиля. Прав это не даёт — права живут в `ClubMember`, а не в `Player.clubId`. Выглядит неожиданно, поэтому названо явно.

### Рейтинг в ответах — строка

`Player.rating` — `Decimal(8,2)`. Наружу он уходит строкой, а не числом: не все такие значения представимы в двоичной плавающей точке, и расхождение вылезет там, где локальный расчёт консоли сравнивается с серверным. Это ровно то, что запрещает запрет №2 брифа, и приоритет №1 из раздела 8.

**Рейтинг при создании игрока не задаётся.** Он проекция журнала `RatingEvent` (ТС 1.4), а вопрос о стартовом значении открыт (ОВ-2) — до его решения действует умолчание схемы.

**Последствия.**

- Роли в клубе проверяются одним декоратором `RequireClubRole`, который включает и проверку токена: забыть второй декоратор легко, и тогда маршрут молча открывается всем
- Право править игрока проверяется в сервисе, а не в guard'е: оно зависит от клуба, записанного у игрока, а не от параметра маршрута
- Отказ «нет такой роли» и «нет такого клуба» выглядят одинаково — иначе перебором идентификаторов узнаётся, какие клубы существуют

## ADR-015. Zod в общем коде подключается как peer-зависимость

**Дата:** 30.08.2026
**Статус:** принято
**Закрывает:** ОВ-10

**Контекст.** Бриф 3.1 требует, чтобы типы, пересекающие границу клиент-сервер, жили в `kttf-shared` и выводились из Zod-схем. ТС 2.1 называет Zod общим средством валидации, ТС 3 показывает `src/types/` со схемами. При этом ADR-тест проверяет `dependencies === {}` у всего пакета, а бриф 3.3 ограничивает требование «ноль зависимостей» только пакетами `rating` и `brackets`.

Тест оказался строже правила, которое стережёт. Пока DTO не существовало, противоречие было отложенным: `kttf-back` держит схемы аутентификации у себя с прямой пометкой «переезжают, когда вопрос будет решён». Каркас фронтенда сделал его срочным — первый же экран входа обязан знать состав ответа ТС 7.1, и продублировать его на клиенте значит нарушить бриф 3.1.

**Решение.** Zod объявляется в `kttf-shared` как `peerDependencies` и `devDependencies`, но не как `dependencies`.

ADR-тест переписывается: вместо запрета зависимостей у пакета целиком он проверяет то, ради чего был написан, — что `src/rating` и `src/brackets` не импортируют ничего, кроме собственных файлов. Проверка по существу, а не по формальному признаку.

**Обоснование.**

_Почему не обычная зависимость._ Экземпляр Zod обязан быть один. Схема, собранная одной копией библиотеки, не проходит `instanceof` в другой, и отказ выглядит как «валидация сломалась без причины». Оба приложения уже ставят Zod сами: `kttf-back` — для валидации запросов, `kttf-front` — под формы (ТС 2.2, React Hook Form + Zod). Peer-зависимость закрепляет то, что и так истинно.

_Почему не отказ от Zod в общем коде._ Рассматривался вариант с рукописными типами DTO и схемами, продублированными в каждом приложении. Он оставляет контракт в двух местах, расходящихся молча, — ровно тот класс ошибок, который бриф запрещает запретом №2 и от которого защищает вся конструкция общего кода.

_Чистота движков не пострадала._ `rating` и `brackets` остаются без единого внешнего импорта: Zod нужен только `types`. Требование брифа 3.3 сформулировано именно про эти два пакета, и оно соблюдается буквально.

**Последствия.**

- `kttf-shared` получает `src/types/` со схемами и выведенными из них DTO
- ADR-тест «у kttf-shared нет ни одной runtime-зависимости» заменяется на проверку импортов `rating` и `brackets`. Формулировка меняется, охраняемое решение — нет
- `kttf-back` переносит `auth.schemas.ts` и схемы клубов и игроков в общий код и импортирует их оттуда
- Перенос — отдельная задача: он меняет три репозитория и требует нового SHA с синхронным `bump-shared` в обоих приложениях (ADR-010)
- До переноса фронтенд не заводит доменных типов у себя. Заглушка `Session` в `kttf-front` содержит только признак входа и заменяется на общий DTO

## ADR-016. Каркас фронтенда: файловые маршруты, оболочки по разделам, обновление по требованию

**Дата:** 30.08.2026
**Статус:** принято
**Уточняет:** ADR-004

**Контекст.** ТС 2.2 называет библиотеки, но не устройство приложения. Каркас — тот момент, когда решения принимаются молча и потом не пересматриваются: расположение маршрутов, точка проверки прав, момент обновления service worker, способ локализации.

**Решение.**

_Маршруты файловые, дерево генерируется плагином._ Компоненты маршрутов автоматически выносятся в отдельные чанки. Для консоли это не удобство, а исполнение ADR-004.

_Компоненты маршрутов не экспортируются._ Проверено: экспорт компонента отключает его вынос в отдельный чанк, и маршрут уезжает в основной бандл. Ленивая загрузка консоли важнее горячей замены при разработке, поэтому правило `react-refresh/only-export-components` для `src/routes` выключено.

_Четыре оболочки вместо одной._ Публичная часть, кабинет, консоль и экран зала не сводятся к общему макету. Общая обёртка означала бы, что зависимости публичной части попадают в чанки консоли, — прямое нарушение бюджета ТС 8.1.

_Права проверяются в одной точке ветки._ Охрана кабинета живёт в `beforeLoad` группы `_app`, а не на страницах. Это не защита данных: по ТС 8.3 права проверяет бэкенд, интерфейс лишь не показывает недостижимого.

_Контекст роутера заведён сразу._ Добавить его позже — значит править каждый файл маршрута, а к MVP их будут десятки.

_Service worker не обновляется сам._ `registerType: 'prompt'`. Автоматическая перезагрузка вкладки может застать судью посреди турнира; приоритет №2 брифа ставит надёжность консоли выше свежести версии.

_Precache берёт весь собранный набор._ Не перечень файлов, который забудут дополнить. Чанки консоли попадают в него по построению.

_Локализация — собственный типизированный словарь, без библиотеки._ ТС 2.2 не называет средства локализации, а бриф 3.4 запрещает захардкоженные пользовательские строки с первой же страницы. Тип ключа выводится из русского словаря, поэтому пропуск ключа в казахском не компилируется. Выбор библиотеки не предрешён: если задача локализации (ТЗ 11) потребует множественных форм и подстановок, переезд затрагивает один модуль.

**Обоснование.** Все пять решений объединяет одно: цена обратного шага. Каждое из них дёшево принять на пустом каркасе и дорого поменять на пятидесяти маршрутах.

**Последствия.**

- ТС 2.2 дополнена строкой о локализации, версия Vite приведена к установленной (ADR-005: числа версий — ориентир)
- Автотест на precache чанков консоли, которого требует ADR-004, и проверка бюджета 400 КБ отложены владельцем продукта и записаны в технический долг
- Импорт из публичных фич в `features/console` запрещён; правило пока не проверяется автоматически

## ADR-017. Сессия на клиенте: refresh-токен на диске, access-токен в памяти

**Дата:** 30.08.2026
**Статус:** принято
**Уточняет:** ADR-013

**Контекст.** ТЗ 2.1 требует сессию на 90 дней с продлением при активности. ADR-013 задал время жизни access-токена в 15 минут: у JWT нет отзыва, и это граница, за которой отозванная сессия перестаёт быть опасной. Значит что-то обязано пережить закрытие вкладки, а что-то — не обязано.

Отдельно требовалось убедиться, что запрет №10 брифа не нарушается: он запрещает `localStorage` для данных турнира.

**Решение.**

- **Refresh-токен** — в `localStorage`, единственным местом записи служит `token-storage.ts`
- **Access-токен** — только в памяти, на диск не попадает никогда
- Истёкший access-токен обновляется прозрачно: один повтор запроса, не больше
- Обновление на всех одно: параллельные запросы, получившие 401 одновременно, ждут общей попытки

**Обоснование.**

_Почему не всё в памяти._ Тогда каждая перезагрузка страницы — новый вход по СМС. Это прямо нарушает ТЗ 2.1 и бьёт именно по судье: вкладка выгрузилась в зале — турнир встал, а кода при отсутствующем провайдере (ОВ-9) взять неоткуда.

_Почему не httpOnly cookie._ Вариант устойчивее к XSS, но ТС 7.1 возвращает токены в теле ответа. Переход означает правку контракта, бэкенда и защиту от CSRF — отдельная задача на три репозитория, а не деталь экрана входа.

_Почему запрет №10 не нарушен._ Он про данные турнира: их место в IndexedDB через Dexie, потому что там объёмы и требования к надёжности. Одна строка токена к этому классу не относится.

_Что принимается как риск._ XSS уводит refresh-токен. В веб-хранилищах защиты от этого нет нигде — ни в `localStorage`, ни в IndexedDB. Реальная мера — httpOnly cookie, и она выше названа отложенной.

_Почему обновление одно на всех._ Сервер заменяет refresh-токен при каждом обновлении (ADR-013). Второе обновление тем же токеном обречено, и без общей попытки три параллельных запроса выбросили бы человека наружу на ровном месте.

**Последствия.**

- Маршруты аутентификации выполняются **вне механизма обновления**. Иначе отказ на `/auth/refresh` запускает обновление, которое дожидается само себя, и запрос зависает навсегда. Дефект был найден тестом при реализации и закрыт признаком `anonymous` у запроса
- Восстановление сессии при запуске — два запроса: `refresh` отдаёт только пару токенов, состав пользователя приходит из `/auth/me`
- Пока сессия восстанавливается, маршруты не отрисовываются: иначе перезагрузка страницы кабинета показывает форму входа вошедшему человеку
- Выход гасит сессию и на сервере, но недоступность сервера не мешает выйти локально

## ADR-018. Турниры: состав участника, лист ожидания, удаление

**Дата:** 30.08.2026
**Статус:** принято
**Уточняет:** ADR-014

**Контекст.** ТЗ 4 задаёт жизненный цикл, поля и правила регистрации, но три вещи в нём не определены, а без них домен турниров не собирается.

**Решение.**

_Участник подтверждается сразу при записи._ ТЗ 4.4 определяет «Подтверждён» как «оплатил и допущен», и только этот статус попадает в таблицу. Оплата — `[V2]`, ручная галочка «оплатил» запрещена запретом №5, где проходит граница — открытый ОВ-6. Пока взнос не собирается, из определения работает только «допущен»: прошёл проверку и есть место — значит подтверждён. Никакой галочки при этом не появляется, и когда придёт оплата, шаг встроится между записью и подтверждением, не меняя остального.

_Освободившееся место занимает первый из листа ожидания._ ТЗ 4.3 требует и список ожидания, и отмену регистрации, но молчит о том, что происходит между ними. Продвижение автоматическое, очередь по времени записи, в той же транзакции, что и освобождение. Иначе список бесполезен: организатору пришлось бы следить за ним руками ровно тогда, когда он занят турниром. Уведомление о продвижении — `[V2]`, его пока нет.

_Удаляется только черновик._ Для опубликованного турнира в ТЗ 4.1 есть отдельный переход — отмена. Жёсткое удаление снесло бы регистрации каскадом, а турнир уже видели игроки.

**Ещё три правила, принятые здесь же.**

- **Черновик виден только тем, кто управляет клубом.** Отказ тот же, что для несуществующего турнира: иначе перебором идентификаторов узнаётся, какие черновики есть
- **Начатый турнир не правится.** Схема проведения уже развёрнута в сетку, а планки уже отработали при записи. Менять их задним числом — получить состав, не соответствующий условиям
- **После старта участника снимают, а не удаляют.** Он уже в сетке; сыгранное остаётся, несыгранное уходит соперникам технической победой (ТЗ 4.4, ADR-009)

**Права — продолжение ADR-014.** Читать турниры может кто угодно без токена; создавать, править и двигать по статусам — владелец и организатор клуба-хозяина. Судья турниром не управляет: по ТЗ 1 его доступ — консоль конкретного турнира. Клуб берётся из самого турнира, а не из адреса маршрута, поэтому проверка живёт в сервисе, а не в guard'е, — так же, как право править игрока.

**Последствия.**

- Появился `OptionalJwtGuard`: календарь открыт всем, но черновики в нём видит их автор. Недействительный токен там не отказ, а анонимный запрос — иначе просроченный токен в фоновой вкладке ломал бы публичную страницу
- Дедлайн регистрации проверяется при записи, а не переводом статуса по расписанию: фоновых задач ещё нет, а без проверки дедлайн не значил бы ничего
- Схема проведения разбирается Zod-схемой при чтении из базы: колонка `Json` типа не имеет, и подмена вылезет здесь, а не в консоли судьи посреди турнира

## ADR-019. Сетка разворачивается целиком: у встречи может не быть участников

**Дата:** 30.08.2026
**Статус:** принято

**Контекст.** Модель `Match` в первой редакции требовала обоих игроков: `playerAId String`, `playerBId String`. Движок сеток из общего кода возвращает встречи, у которых участник задан источником — `PARTICIPANT`, `WINNER` или `LOSER`. В олимпийской сетке источник `PARTICIPANT` есть только у первого круга: полуфинал — это «победитель такой-то встречи», и записать его было нечем.

Обнаружилось при жеребьёвке. Круговой схемы и групп это не касается: там все пары известны сразу.

**Решение.** `playerAId` и `playerBId` становятся необязательными, добавляются `sourceA` и `sourceB` — `{ kind: 'WINNER' | 'LOSER', matchId }` либо `null`, если участник известен сразу. Сетка разворачивается целиком в момент жеребьёвки.

**Обоснование.**

_Почему не «только первый круг»._ Рассматривался вариант без миграции: создавать встречи по мере того, как определяются участники. Он ломает две вещи. ТЗ 9.4 требует показывать сетку в результатах турнира, а второй экран (ТС 7.7) показывает её по ходу — до конца турнира показывать было бы нечего. И логика достройки уехала бы в обработку результата встречи, где ей не место: сетку строит движок, а не тот, кто вводит счёт.

_Почему источник, а не «пустая встреча»._ Без источника связь между кругами теряется, и восстановить её можно только пересчётом всей сетки заново. Источник — это ровно то, что возвращает движок, и хранится он как есть.

**Последствия.**

- Миграция `20260830180000_match_bracket_sources`
- ТС 4.1 обновлена
- Всякий, кто читает `Match`, обязан считаться с тем, что игрока может не быть. Расчёт таблицы такие встречи пропускает, и это правильно: несыгранной встречи не существует, начислять по ней нечего
- Утешительная сетка (ТЗ 5.1) по-прежнему не строится: движок её не умеет, а собирать сетку в приложении запрещено запретом №2. Жеребьёвка отвергает такую конфигурацию явным отказом, а не молча
